# 2026-10-06 — What is left

**Status:** superseded 2026-10-07 by [`2026-10-07-stages.md`](2026-10-07-stages.md). It was written before EmDash's own CLIs, skills and docs had been read. Its items live on there: the repo-and-admin item is the `sync` stage; the deployment proofs are the `ship` and `rescue` stages; the three-OS run is stage 1; everything about `dev` and the nushell harness ends with stage 9, which deletes it.

## Why it is one list

The three closed plans each ended the same way: everything that can be shown on a laptop was done,
and what stayed open needs a deployment this repo does not have, or one CI run on three OSes. Kept
in three files, that read as three unfinished plans. It is one short list.

The first item is different. It is what using the harness to build a real site showed to be wrong
with the harness itself, and it comes before anything else.

## Items

- [ ] **0. The repo and the admin stay in step, the way EmDash documents it** — a site changes two
  ways: developers and agents through the repo and `mise`, people through the admin by their role.
  EmDash's own guide (`deployment/schema-evolution.mdx`) says how they meet, and the harness does
  the opposite in one place and nothing in the others
  - **Who owns what** (EmDash's rule, not ours): the live database owns the content and the content
    model. The repo owns the code. The seed only makes a *fresh* database; deploying a changed seed
    to a live site does nothing
  - [ ] **live → repo, one flow:** export the deployed model into `site/seed/seed.json` (EmDash's
    recipe: `wrangler d1 export`, then `emdash export-seed`), regenerate the types
    (`emdash types --url`), and say what changed. Run after anyone changes the model in the admin;
    commit the result with the code that uses it. Today `seed:export` reads only the local database
    and writes to `run/` for comparing by hand
  - [ ] **repo → live, one flow:** a model change is made with `emdash schema` (locally, then the
    same commands with `--url`), in EmDash's order — additive changes before the code that uses
    them, removals after the code that stops. `deploy` shows the difference *before* it ships and
    says which side is ahead; today the difference is found only after, by `doctor`
  - [ ] **content never travels through the seed.** People edit it in the admin by role; an agent
    edits the same entries through the CLI or MCP with a token scoped to its role. Bringing live
    content to a laptop is `snapshot -- --url` then `restore -- --wipe`: make it one flag
  - [ ] **stop `dev` writing seed edits over an existing database** (`apply-seed`, `nu/site.nu`): it
    teaches the wrong model and can overwrite what was edited in the admin. A seed edit is tried on
    a fresh database with `reset`
  - [ ] `schema:diff` compares taxonomies and menus as well as collections and fields
  - [ ] `docs/auth.md` says how people actually get in — passkey, magic link, the login providers,
    invitations, Cloudflare Access — and which token an agent uses for which role

- [ ] **1. `dev` does only what changed, and the site stays up** — found on 2026-10-06 by two
  reviews and by building the Remy-Sport site with it. `refresh` (`nu/main.nu`) runs for `setup`,
  `dev`, `plugin:new`, `plugin:remove`, `reset` and a database restore, and every time it validates
  the seed, rebuilds and re-copies every plugin, fetches the EmDash source, deletes the server's
  compile cache and starts it cold
  - [ ] `dev` twice in a row: the second run does not restart the server. Proof: the server's pid is
    the same before and after
  - [ ] a change that needs a restart (a setting, a plugin, the EmDash version) still gets one
  - [ ] a project with no skills to vendor clones nothing, and `dev` works offline
  - [ ] an upgrade cannot be left half done: advice never aborts it, and a second `dev` finishes one
    that was interrupted
  - [ ] going back a version keeps a correctly labelled copy of what it replaces
  - [ ] after `restore -- <package> --wipe --confirm`, the next `dev` leaves the restored content
    alone. Proof: restore, `dev`, the content is still there
  - [ ] `check -- --site` and `deploy --dry` do not stop a running site, or the reason they must is
    proven and written beside the code
  - [ ] the skills check and the backup-and-restore proof can each fail: a fault is planted for each
  - [ ] `nu/*.nu` plus `harness.toml` is under the 1,952 lines it was at the merge

- [ ] **2. The harness keeps its hands off the project's files, and guards a deploy**
  - [ ] `registry:up` edits nothing that is committed: the registry's address reaches the server
    when it starts, and `registry:down` leaves no trace. Proof: `git status` is clean after up, down
  - [ ] the commit hook type-checks the site when a file under `site/` is staged
  - [ ] `deploy` refuses while `site/wrangler.jsonc` still holds the template's names
    (`my-emdash-site`, `my-emdash-media`), and while a `site/.dev.vars` exists that would be built in
  - [ ] `deploy --dry` ends by printing how to preview the build. No new task
  - [ ] `daemon-stop` is given its port instead of guessing it from the daemon's name, and the
    "is the port free" test covers IPv6 as well as `127.0.0.1`
  - [ ] the site daemon's `auto = ["start", "stop"]`: find out whether it starts or stops the site
    when a shell enters or leaves the folder, and remove it if it does

- [ ] **3. Use what EmDash already has, before building it** — the Remy-Sport site was given two
  languages by hand while EmDash's registry held a translation plugin and its guide described the
  whole of i18n. The harness had no way to ask, and its agent guide did not say to
  - [ ] one way to search EmDash's registry from a project (`searchPackages` on the registry the
    site uses), through an existing task if one fits
  - [ ] a registry plugin a project installs is declared in the repo, so a fresh clone and `setup`
    get it — today an install lives only in one machine's database
  - [ ] `docs/agents/README.md` says it in one line: before building a feature into a site, read
    EmDash's guide for it and search the registry
  - [ ] a new site can be created with more than one language: the locale list is one setting

- [ ] **4. Proofs that need a real deployment** — the Remy-Sport site's first deploy supplies one.
  Each is written and unrun; the closed plans name the exact command for each
  - [ ] `deploy` prints the D1 Time Travel bookmark before it ships
  - [ ] `snapshot -- --database --url <deployment>` writes the bookmark, the dump and `restore.txt`,
    and the dump loads into a new empty database
  - [ ] `restore -- <package> --url <deployment> --confirm`, then `doctor -- --url` is healthy
  - [ ] `DEPLOY_TOKEN=… mise run doctor -- --url <deployment>` with no stored sign-in
  - [ ] `doctor -- --url` fails against a database one migration behind
  - [ ] what a free-plan deploy does with the Worker Loader binding, recorded in `docs/emdash.md`
  - [ ] on Node, `deploy`'s closing line says the built server does not read `.env`

- [ ] **5. One full run on three OSes, before the next release — not before**
  - [ ] `gh workflow run "full verification"`: every job green, including the three Upgrade jobs.
    Everything merged on 2026-10-06 has run on macOS only
  - [ ] the Upgrade job's `--from` version comes from a setting, not a hard-coded `1.0.1`
  - [ ] `mise run verify:linux` passes locally first

## The owner's, not the harness's

- The D1 database `emdash-run`, the R2 bucket `emdash-run-media` and a KV namespace are left over
  from the deleted Worker. Keep or delete.
- An upstream issue is written up and not filed: the templates and skills repos have no version
  tags (`docs/emdash.md` § To report upstream, item 6).
- The Remy-Sport app's authorization fix is on a local branch, unpushed and undeployed.

## How our own repos take the harness

From `main` on this machine: `mise run upgrade -- main --from <path to this checkout>`. A release is
for developers outside, and is cut when they need something — not to move a fix between our repos.
