## The setup wizard of a deployed site — what it offers

Read on 2026-10-07 on the proof site (`/_emdash/admin/setup`, step 1 on screen; steps 2 and 3 from
`packages/admin/src/components/SetupWizard.tsx` and `guides/authentication.mdx`, because going on
from step 1 submits it). The first version of this plan knew only "a passkey". There is more, and
it changes stage 6.

| step | what it offers | what that means here |
|---|---|---|
| 1 · Site | title and tagline; then **Sample content**, **Empty site**, or **Import an existing EmDash site** — "once setup is done, upload a .emdash package exported from another EmDash site" | **Import is how a site built locally gets its content onto its first deployment.** `mise run emdash -- site export --output …` on the local site, then this option. Nothing in this plan carried local content to a deployment before |
| 2 · Account | the administrator's email and name | the email is stored unverified when a passkey is used |
| 3 · Sign In | **a passkey**, and under "Or continue with", **every login provider the site configures**: GitHub, Google, Microsoft, Atmosphere. The proof site configures none, so it shows the passkey only | a provider is site code (`authProviders` in `astro.config.mjs`) plus that provider's client id and secret as Worker secrets |
| instead of 3 | **Cloudflare Access**, when the site sets the `auth` option: the wizard says "You're signed in via Cloudflare Access" and asks for nothing. In production it is then the *only* way in — no passkeys, providers, magic links or invites — and the first person through becomes Admin | the owner's Cloudflare account decides who gets in, by identity provider and group; roles can be mapped from groups |

Why EmDash's development sign-in is not on this list: its route begins
`if (!import.meta.env.DEV) return 403`, and that value is fixed when the site is built — true under
`astro dev`, false in every `astro build`. A development build could be deployed, and then anyone
who opened the address would be administrator. Not done.

What none of these gives an agent: a way in without a person. After a person is in, the agent's
way is `emdash login --url` (a code the person approves once) — or, under Cloudflare Access, what
Access itself allows; that has not been read or tried yet.

**Decisions this puts to the owner, for the Remy-Sport site** (stage 6): passkey, a login provider,
or Cloudflare Access; and whether its first deployment starts from an import of the local site.

## The tasks this plan built

| task | steps — as they ran |
|---|---|
| `live:ship` | `step:live` (is `LIVE_URL` set) → `wrangler whoami` → `live:check` → `wrangler deploy --strict --message "live:ship <time>"` → `wrangler deployments status` → `curl --head LIVE_URL` |
| `live:undo [version]` | `wrangler whoami` → `wrangler rollback [version] --yes --message "live:undo"` → `wrangler deployments status` → `curl --head LIVE_URL` |
| `live:logs` | `wrangler tail` |
| `live:key` | `wrangler whoami` → `wrangler secret bulk .env` → `wrangler secret list`, behind a `confirm` |
| `live:backup` | `wrangler whoami` → `wrangler d1 time-travel info DB` → `emdash site export --url LIVE_URL` → what each copy is and is not |
| `model:sync -- --live` | `emdash types --url LIVE_URL`, then what git sees |

What running them changed from the plan:

- **No migration step.** `emdash migrate --check` against D1 needs a Cloudflare API token and
  account id of its own; wrangler's sign-in is not enough ("A valid Cloudflare account ID is
  required for D1 migrations"). It is EmDash's pipeline mode. In the default mode EmDash migrates
  on the first request, which `live:ship` makes and waits for.
- **No bookmark before a deploy.** On a first deploy there is no database yet, so the step would
  fail the task. Time Travel restores to a time as well as to a bookmark, and
  `wrangler deployments list` has the time of every deploy. The bookmark is in `live:backup`.
- **No SQL dump.** G13 is confirmed on a deployed database: "D1 Export error: cannot export
  databases with virtual tables (like FTS5)".
- **The last step is `curl`**, not one of EmDash's commands: `emdash whoami` exits 0 whatever
  happens, and every other command answers "Not authenticated" until a person has set the site
  up. `curl` is on macOS, Linux and Windows.
- **`live:key` is its own task**, run once after the first `live:ship`. EmDash's documented
  `wrangler secret put` asks for the value at a prompt; `wrangler secret bulk .env` takes the
  file, so no value is typed or shown. It is refused while a rolled-back version is live
  (Cloudflare's error 10215) — ship first.
