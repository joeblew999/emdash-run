# 2026-10-07 — Sign-in: nothing may wait on a person at a browser

**Status:** closed 2026-10-07 — merged into [`../2026-10-07-next.md`](../2026-10-07-next.md). Three plans
with 42 open boxes between them had stopped being a plan. What is ticked here was done and is the
record of how; every box still open was carried into the one plan, or dropped there with the reason.

The owner, 2026-10-07: asking for a passkey "will be impossible for you to quickly develop the
cli", "you need to some how automate this aspect", passkeys are "too machine focussed", and "if
there are many options then consider using many for the different aspects that make sense".

So this is not one answer. There are four different things that need a way in, and each gets the
option that fits it.

## What EmDash gives — read and run, 2026-10-07, EmDash 1.2.0

| | |
|---|---|
| Development mode (`astro dev`) | EmDash's dev sign-in: no person, no credential. Compiled out of every build: the route starts `if (!import.meta.env.DEV) return 403` |
| A build — deployed, or served on this machine with `astro preview` | the setup wizard, then real sign-in. **A build on `localhost` behaves exactly like a deployment:** run — `/_emdash/admin` → `/setup`, dev sign-in 403 |
| The first administrator | wizard: a passkey, or any login provider the site configures (GitHub, Google, Microsoft, Atmosphere), or nothing at all under Cloudflare Access |
| Later sign-in | passkey; "Sign in with email link" (needs an email provider); a login provider; or Cloudflare Access, which in production replaces all the others |
| The CLI | `emdash login --url`: prints a code, a signed-in administrator approves it at `/_emdash/admin/device`. **The credential is saved per project folder** ("Token saved to path:<site folder>"), so signing in from one project does nothing for another. Or `EMDASH_TOKEN`, a personal access token made in the admin |
| The CLI behind Cloudflare Access | `emdash login` tries `cloudflared`, else `-H "CF-Access-Client-Id: …" -H "CF-Access-Client-Secret: …"` (or `EMDASH_HEADERS`). Read in `cli/commands/login.ts`, **not run**. The Access module wants an `email` in the token, which a service token does not have — so a service token may only get the CLI *through* Access, with EmDash's own code approval still to come |
| A setting that makes an administrator or a token without a browser | **none.** Every `EMDASH_*` variable in the source was listed; there is no bootstrap one |

## The four aspects, and what each uses

| aspect | what it needs | option chosen | state |
|---|---|---|---|
| **A. Building and testing the tasks that need a signed-in site** — `live:backup`'s package, `content:pull`, `model:sync -- --live`, anything written through the CLI. This is the fast loop | a site with real sign-in, as often as wanted, with nobody there | **a production build on this machine, set up by a script**: `astro build`, `astro preview --background`, then Playwright drives EmDash's own wizard with Chrome's simulated passkey device and approves `emdash login`'s code | **prototyped and working**: `prototypes/first-admin.mjs` |
| **B. Deploying itself** — `live:ship`, `live:undo`, `live:logs`, `live:key`, the database bookmark | Cloudflare only, no EmDash sign-in | wrangler's stored login | **done**, in the live plan |
| **C. People on a deployed site** — the owner, editors | not a passkey per machine | to be chosen in stage 3 from: a login provider (GitHub or Google); Cloudflare Access; email link. Each is tried on a local production build first | not started |
| **D. An agent or CI on a deployed site** — the same tasks as A, against the real thing | a credential that exists without a person at a browser each time | in order of preference: (1) whatever stage 3 shows Access service tokens can do; (2) `EMDASH_TOKEN` from a gitignored file, the token made once by a person; (3) the stage-1 script pointed at the deployment, run as one command by the owner or by CI | not started |

**One limit that no tool changes.** The agent working in this repo does not create an account or
sign in on a site that is not on this machine — not through the wizard, not through a script, not
through the database. That is why A is the main road: on this machine there is no such limit and
no person is needed. For D, the plan makes the one-time act a single command or a single file,
never a browser session, and whoever runs it is the owner or CI.

  | who | way in | why |
  |---|---|---|
