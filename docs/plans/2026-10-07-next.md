## Sign-in, settled by running it — 2026-10-07 evening

**A machine gets in with one thing: an EmDash API token.** EmDash accepts a bearer token before
any other sign-in — under Cloudflare Access too (`astro/middleware/auth.ts`) — and its own dev
sign-in mints one (`dev-bypass?token=1`). `admin/token.mjs` does the same for a production build:
it writes an administrator, the three "set up" options and the token's hash into the site's D1
with wrangler. No browser, no Playwright, no passkey, no approval code.

| | result |
|---|---|
| `site:token` on a fresh local production build | "needsSetup": true → false; then, with no token typed anywhere, `emdash whoami --url` → "Role: admin, Auth: token"; a page created; `model:sync -- --live` and `content:pull` exit 0 |
| `live:access`, run as `fnox exec -- mise run live:access` on the proof site | the owner's fnox `CLOUDFLARE_API_TOKEN` can create Access applications, policies and service tokens. Wrangler's own login cannot: 403 |
| Cloudflare Access in front of the proof site | admin and API → the Access login; the public page → 200 |
| a service token | gets a machine *through* Access (`/setup/status` → 200), and is not a user (`/auth/me` → 401). Takes a few seconds after the policy is made |
| `emdash login` under Access | "Device Flow is not available for this instance. Generate an API token in Settings > API Tokens" — which is the token above |
| `live:token` against the proof site | **not run yet** |
| a person signing in through Access | **not run yet** — needs the code Cloudflare emails |

How the pieces fit: `mise run emdash -- … --url <site>` goes through `admin/emdash.mjs`, which adds
whatever this machine has saved for that site's host — the API token (`site:token`, `live:token`)
and the Access pass (`live:access`). The dev's Cloudflare token comes from fnox:
`fnox exec -- mise run live:…`. fnox is in this repo's `[tools]`.

Found on the way: `emdash login` saves its sign-in **per project folder**, not per site. After the
Playwright script (`site:admin`) had run, emptying the local database left that sign-in stale and
`mise run emdash` on the dev site failed with "Token is invalid or expired" until
`emdash logout`. The token route never calls `emdash login`.

**All the ways are kept, side by side, as `signin:*` tasks** (the owner: "KEEP the other ways too! we
will need to try them out"). Each takes `--live` for the deployed site. The comment block above
them in `tasks.toml` says what each is for.

| task | for | proven on a fresh local production build, 2026-10-07 |
|---|---|---|
| `signin:token` | a machine, no browser — "the sneaky way" | `whoami` → Role: admin, Auth: token |
| `signin:passkey` | a machine, through EmDash's real wizard and CLI login | "first administrator created", "cli: signed in"; `whoami` → Auth: stored |
| `signin:open` | a person: a visible signed-in window | "open: signed in … My Site Dashboard" |
| `signin:access` | people on a deployed site, by Cloudflare Access; plus a pass for machines | on the proof site, with the fnox token |
| `site:admin` (hidden) | a fresh build + the passkey way, in one | still works by name |

On the deployed proof site, checked and ready for `signin:token -- --live`: the fnox token reaches
its D1 (0 users, 0 tokens, not set up); the CLI gets through Access with the saved pass and
reaches EmDash, which answers 401 because no token exists yet.

**Then run, on the deployed proof site behind Access — all through mise, no browser:**
`fnox exec -- mise run signin:token -- --live` → "is an administrator of https://emdash-run-proof…";
`emdash schema list --url` → pages, posts; `content create` and `content get` → the page is there;
`schema add-field` then `model:sync -- --live` → the field is in `.emdash/schema.json`;
`content:pull` → a package in `backups/`; `fnox exec -- mise run live:backup` → the Time Travel
bookmark and a 15-file package. The public page answers 200; the admin without the pass → 302 to
Access. One thing fails: `emdash whoami --url` prints "Unexpected token '<'" — EmDash's `whoami`
does not send the extra headers (its docs list `--header` for the other commands, not `whoami`),
so it gets the Access login page. Use `schema list` to check a deployed sign-in.

Security is deliberately not being worked on now (the owner: "stop worrying about security. we
will come back to that later. this is all just test sites"). No CI either until the owner says.

Still here, not yet decided: the Playwright script (`site:admin`, `site:open`) — the token route
does its job in a second — and the two service tokens on the proof application
(`emdash-run-proof:emdash-run` is the saved one; `emdash-run-proof:probe` has no known secret).

  kind of credential. The real-deployment run is stage 3, on a site that is wanted.

  in production it switches off every other sign-in, the script's passkey included.
- **Email-link sign-in.** Needs an email service first; GitHub gives people the same thing with
  less to set up.
- **A git hook for `site:check`.** Decided against in the stages plan.
