## The idea

A dev or an agent thinks in stages: *start working, check my work, keep the admin and the repo in
step, put it live, add a plugin, move to a new EmDash, get out of trouble.* Each is a visible `mise`
task, and a task is nothing but EmDash's own commands in the right order.

- **All of it is mise.** The tasks live in one `tasks.toml`. No nushell and no JavaScript underneath.
- **DRY by hidden tasks.** A step that more than one task needs is a hidden task (`step:…`); the
  visible tasks are sequences of them. A task can also run a whole other task.
- **A project gets them with one line** in its `mise.toml`:
  `[task_config] includes = ["git::https://github.com/joeblew999/emdash-run.git//tasks.toml?ref=<tag>"]`.
  Nothing is copied into the project. The project also names its tools — `[tools] node`, `pnpm` —
  because an include cannot carry them and a per-task declaration is silently lost on a hidden step.
- **A step may exist only for a proven gap** (`docs/agents/README.md` § EmDash first). Where EmDash
  — or Astro, or wrangler — has a command, the step is that command.

Every visible task is `<what>:<verb>`, with mise's own `:`. They group in `mise tasks ls`, complete
by namespace, and do not collide with a project's own tasks. Hidden steps are `step:*`.

### `site:new` — a site, once · built

`pnpm dlx create-emdash@latest site --template <template> --pm pnpm --install --yes`.

- The template is `<platform>:<template>`, as the scaffolder spells it — eight choices: `blog`,
  `starter`, `marketing`, `portfolio` on `cloudflare` or `node`. Given as an argument
  (`mise run site:new -- node:blog`), else the `TEMPLATE` setting, else `cloudflare:blog`. A name
  not in the list is refused by mise and nothing is made.
- Its own task because mise cannot skip a step that is already done (G1), and because EmDash
  treats it as one: `npm create emdash`.
- Run: all eight choices made the platform asked for — `wrangler.jsonc`, D1 and R2 for
  `cloudflare:*`; the Node adapter, SQLite and local uploads for `node:*`.

### `site:start`, `site:stop`, `site:logs` — I want to work on this site · built

`step:install` → `step:key` → `step:seed` → `step:dev` → `step:up`. It returns in seconds with the
site running in the background.

- Opening EmDash's **Dev bypass** link once sets the site up with the seed's sample content and
  signs you in (`…/_emdash/api/setup/dev-bypass?redirect=/_emdash/admin`; `&content=0` for an
  empty site). A person clicks it; an agent requests it. Checked in a real browser: the dashboard
  loads, signed in as an administrator, no console errors.
- The CLI and `mise run emdash -- …` work at once, with no token.
- `site:stop` is `astro dev stop`; `site:logs` is `astro dev logs --follow`. Running `site:start`
  again leaves a running site alone — Astro's own lock says it is already up.

### `site:delete` — the opposite of `site:new` · built

`site:stop` → `step:delete`, behind a `confirm`. Added at the owner's request, to try both.

- Asks at a terminal (answered with `y`: stopped the server, removed `site/`, no process left).
  Refuses when nobody can answer. **In CI it does not ask** — mise answers yes when `CI` is set.
- Rough edge: with no `site/` it ends in a bare "No such file or directory" from `site:stop`.

### `emdash` — anything else · built

`pnpm exec emdash` with whatever follows `--`, aimed at this project's port. Content, schema,
media, menus, taxonomies, search, secrets.

### `site:check` — is my work sound, before a commit · to build

`step:install` → `step:seed` → `step:typecheck` → `step:build`.

- Plugins: `pnpm run validate`, `typecheck`, `test`, `build` in each (`your-first-plugin.mdx`
  L167-172), then `emdash-plugin bundle --validate-only` (`cli.mdx` L128). Reaching every plugin
  without a loop is Q3.
- A git hook runs it. (The old hook was disabled on 2026-10-07; nothing runs on commit today.)

### `site:reset` — the local site back to its seed · to build

`site:stop` → `pnpm dlx rimraf .wrangler/state data.db data.db-wal data.db-shm uploads` →
`site:start`. Local only; behind a `confirm`.

### `model:sync` — the admin and the repo must agree · to build

EmDash's rule (`schema-evolution.mdx` L10-21): the live database owns the content and the model, the
repo owns the code, the seed only makes a fresh database.

- `step:up` → `step:types` → `git diff --stat -- .emdash/schema.json`. Run it after anyone changes
  the model, in the admin or with `emdash schema`; commit what it wrote with the code that uses it.
  With `EMDASH_URL` set to a deployment it records the live site's model instead.
- Changing a live model stays EmDash's: the admin, or `mise run emdash -- schema add-field … --url`,
  additive changes before the code that uses them, removals after (`schema-evolution.mdx` L126).
- Refreshing `seed/seed.json` from a database is `emdash export-seed`, which reads a SQLite file
  only — G3.

### `content:pull` — a live site's content, on this machine · to build

`step:package` from the deployment, then it prints the two import commands. The import is reviewed
by a person on purpose: `emdash site import <file> --analyze`, read the plan, then
`--plan <digest> --confirm` (`site-transfer.mdx` L230-249). Into an empty local site.

### `plugin:new`, `plugin:add`, `plugin:publish` — I need a plugin · to build

- **`plugin:new <name>`** — `pnpm dlx @emdash-cms/plugin-cli init <name> --yes --publisher …` in
  `plugins/`, `pnpm install`, `pnpm run test`, `pnpm run build`, then in the site
  `pnpm add file:../plugins/<name>` — EmDash's documented way (`your-first-plugin.mdx` L186-205).
  It ends by printing the two lines to add to `astro.config.mjs`: the import and `sandboxed: [name]`.
- **`plugin:add <package>`** — `pnpm add <package>` in the site, and the same two lines
  (`installing.mdx` L132-150). The plugin is then declared in the repo and a fresh clone has it.
- **`plugin:publish <name>`** — `emdash-plugin validate` → `bundle --validate-only` → `publish`, or
  `release setup` once for releases from GitHub Actions with provenance
  (`delegated-releases.mdx` L33-100).
- Finding one is `emdash-plugin search <words>`; a hidden passthrough for the plugin CLI comes with
  this work.
- Installing from the registry is done in the admin, by an administrator, with a consent dialog
  (`installing.mdx` L63-71). No command exists and the install is not in the repo — G5.

### `live:ship`, `live:undo` — put it live · to build

`site:check` (the whole task) → `step:mark` → `pnpm exec emdash migrate --status` →
`pnpm exec wrangler deploy` → `step:migrations` → `pnpm exec emdash whoami --url <DEPLOY_URL>`.
(`cloudflare.mdx` L85-93, `core-migrations.mdx` L16-28.)

- **`live:undo`** — `pnpm exec wrangler rollback`, then `step:migrations`; it says that a rollback
  does not undo a migration (`core-migrations.mdx` L178).
- On Node the task ends at the build and prints how to start it:
  `node --env-file=.env ./dist/server/entry.mjs` (`nodejs.mdx` L395-402).
- What must be true before a first deploy, and cannot be checked by a command today, is printed as
  a list — G6.

### `live:backup` — a copy, or a way back · to build

Three different copies, never confused (`site-transfer.mdx` L120-127):

- `step:mark` → `step:dump` → `step:package`. The bookmark and the SQL dump are the disaster
  recovery (users, tokens and plugin data included); the package is the portable copy (content,
  model, media; no users). It ends by saying what none of them holds: the media bucket
  (`aws s3 sync`, `backups.mdx` L59-71) and `EMDASH_ENCRYPTION_KEY`.
- Restoring is printed, not run: `wrangler d1 time-travel restore` and loading a dump are
  destructive and need a person to choose the moment (`backups.mdx` L77-95).

### `emdash:update` — a newer EmDash · to build

`step:mark` → `step:dump` → `pnpm outdated emdash @emdash-cms/cloudflare` →
`pnpm up --latest emdash @emdash-cms/cloudflare` → `step:build` → `pnpm dlx skills update`
(`updating.mdx` L333-365, `agent-skills.mdx` L322-329). It ends with the release-notes address and
the reminder that template files are not updated. Then `site:start` to see it run, `live:ship` to
deploy it.

## Not tasks, on purpose

- **Content** — people in the admin by their role; agents through `mise run emdash -- content …` or
  the site's MCP server with a scoped token (`ai-tools.mdx`).
- **Site code** — pages, queries, rendering, SEO, languages: written from the
  `building-emdash-site` skill; `site:check` verifies it.
- **People and access** — passkeys, login providers, invitations, Cloudflare Access: configuration
  and the admin (`authentication.mdx`).
- **Migrating from WordPress** — a one-off, with EmDash's importer and its two WordPress skills.
- **Themes** — a theme is a template; there is no theme command (`themes/overview.mdx` L8-10).
