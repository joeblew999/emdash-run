# 2026-10-07 — The stages: everything a dev or agent does on an EmDash site, as a few mise tasks

**Status:** active — **0 of 9 stages done**. The only open plan. It replaces
[`done/2026-10-06-open.md`](done/2026-10-06-open.md), which was written before EmDash's own tooling
had been read.

## The idea

A dev or an agent thinks in stages: *start working, check my work, keep the admin and the repo in
step, put it live, add a plugin, move to a new EmDash, get out of trouble.* Each stage is one visible
`mise` task. A stage is nothing but EmDash's own commands, in the right order.

- **All of it is mise.** The tasks live in one `tasks.toml`. No nushell and no JavaScript underneath.
- **DRY by hidden tasks.** A step that more than one stage needs is a hidden task (`step:…`); the
  visible stages are sequences of them. A stage can also run a whole other stage.
- **A project gets them with one line** in its `mise.toml`:
  `[task_config] includes = ["git::https://github.com/joeblew999/emdash-run.git//tasks.toml?ref=<tag>"]`.
  Nothing is copied into the project.
- **A step may exist only for a proven gap** (`docs/agents/README.md` § EmDash first). Where EmDash
  has a command, the step is that command.

## Names

Every visible task is `<what>:<verb>`, with mise's own `:` — they group in `mise tasks ls`, complete
by namespace, and never collide with a project's own tasks. Hidden steps are `step:*`.

| namespace | tasks | the stage below |
|---|---|---|
| `site:` | `site:new`, `site:delete`, `site:start`, `site:stop`, `site:logs`, `site:check`, `site:reset` | new, start, check, and the local half of rescue |
| `model:` | `model:sync` | sync |
| `content:` | `content:pull` | sync:content |
| `plugin:` | `plugin:new`, `plugin:add`, `plugin:publish` | plugin |
| `live:` | `live:ship`, `live:undo`, `live:backup` | ship, and the deployed half of rescue |
| `emdash` | `emdash` (the CLI), `emdash:update` | emdash, update |

The stage sections below still use the short names they were written with; the table is the mapping.
`site:delete` was added on 2026-10-07 at the owner's request: the opposite of `site:new`, with a
confirmation.

## The stages

Visible tasks are **bold**. `step:*` tasks are hidden and shared. Every command runs in `site/`.

### Shared hidden steps

| step | command | used by | source |
|---|---|---|---|

| `step:seed` | `pnpm exec emdash seed --validate` | start, check | `reference/cli.mdx` L100 — an invalid seed is skipped on the first request with no error (`schema-and-seed.md` L535) |
| `step:dev` | `pnpm exec astro dev --background --host 127.0.0.1 --port <SITE_PORT>` — Astro keeps the pid, the log and a lock, and says so when one is already running | start | `astro dev --help` |

### 1. **`new`** — a site, once

`pnpm dlx create-emdash@latest site --template {{env.TEMPLATE}} --pm pnpm --install --yes`
(`create-emdash --help`; `TEMPLATE` as the scaffolder spells it: `cloudflare:blog`, `node:starter`;
`-- --sandboxed-plugins` passes through). Its own stage because mise cannot skip a step that is
already done, and because EmDash treats it as one: `npm create emdash`.

### 2. **`start`** — I want to work on this site

`step:install` → `step:seed` → `step:dev` → `step:up`. It returns in seconds with the site running.

- Opening EmDash's **Dev bypass** link once sets the site up with the seed's sample content and
  signs you in (`…/_emdash/api/setup/dev-bypass?redirect=/_emdash/admin`; `&content=0` for an
  empty site). A person clicks it; an agent requests it.
- The CLI and `mise run emdash -- …` work at once, with no token.
- **`stop`** is `astro dev stop`; **`logs`** is `astro dev logs --follow`. Running `start` again
  leaves a running site alone — Astro's own lock says it is already up.
- **Run on 2026-10-07, macOS, EmDash 1.2.0, from an empty folder:** `new` 13s (site, skills,
  `.mcp.json`, `AGENTS.md`, `.env`); `start` 6s; admin redirected to `/setup` and 0 posts before
  the link, 8 posts and a 200 home page after; a draft created through `mise run emdash --` with a
  quoted JSON argument; second `start` left pid 61290 alone; `stop` stopped it.

### 3. **`check`** — is my work sound, before a commit

`step:install` → `step:seed` → `step:typecheck` → `step:build`.

- Plugins: `pnpm run validate`, `typecheck`, `test`, `build` in each (`your-first-plugin.mdx`
  L167-172), then `emdash-plugin bundle --validate-only` (`cli.mdx` L128). How one stage reaches
  every plugin without a loop is open question Q3.
- The git hook runs this stage.

### 4. **`sync`** — the admin and the repo must agree

EmDash's rule (`schema-evolution.mdx` L10-21): the live database owns the content and the model, the
repo owns the code, the seed only makes a fresh database.

- **`sync`** — `step:up` → `step:types` → `git diff --stat -- .emdash/schema.json`. Run it after
  anyone changes the model, in the admin or with `emdash schema`; commit what it wrote with the code
  that uses it. With `EMDASH_URL` set to a deployment it records the live site's model instead.
- **`sync:content`** — `step:package` from the deployment, then prints the two import commands.
  The import is reviewed by a person on purpose: `emdash site import <file> --analyze`, read the
  plan, then `--plan <digest> --confirm` (`site-transfer.mdx` L230-249). Into an empty local site.
- Changing a live model stays EmDash's: the admin, or `mise run emdash -- schema add-field … --url`,
  additive changes before the code that uses them, removals after (`schema-evolution.mdx` L126).
- Refreshing `seed/seed.json` from a database is `emdash export-seed`, which reads a SQLite file
  only — gap G3.

### 5. **`plugin`** — I need a plugin

- **`plugin:new <name>`** — `pnpm dlx @emdash-cms/plugin-cli init <name> --yes --publisher … ` in
  `plugins/`, `pnpm install`, `pnpm run test`, `pnpm run build`, then in the site
  `pnpm add file:../plugins/<name>` — EmDash's documented way (`your-first-plugin.mdx` L186-205).
  It ends by printing the two lines to add to `astro.config.mjs`: the import and `sandboxed: [name]`.
- **`plugin:add <package>`** — `pnpm add <package>` in the site, and the same two lines
  (`installing.mdx` L132-150). The plugin is then declared in the repo and a fresh clone has it.
- **`plugin:publish <name>`** — `emdash-plugin validate` → `bundle --validate-only` → `publish`, or
  `release setup` once for releases from GitHub Actions with provenance
  (`delegated-releases.mdx` L33-100).
- Finding one is `mise run emdash-plugin -- search <words>` (hidden passthrough).
- Installing from the registry is done in the admin, by an administrator, with a consent dialog
  (`installing.mdx` L63-71). No command exists and the install is not in the repo — gap G5.

### 6. **`rescue`** — a copy, or a way back

Three different copies, never confused (`site-transfer.mdx` L120-127):

- **`rescue`** — `step:mark` → `step:dump` → `step:package`. The bookmark and the SQL dump are the
  disaster recovery (users, tokens and plugin data included); the package is the portable copy
  (content, model, media; no users). It ends by saying what none of them holds: the media bucket
  (`aws s3 sync`, `backups.mdx` L59-71) and `EMDASH_ENCRYPTION_KEY`.
- **`rescue:reset`** — the local site back to its seed: `pnpm dlx rimraf .wrangler/state data.db
  data.db-wal data.db-shm uploads`. Local only.
- Restoring is printed, not run: `wrangler d1 time-travel restore` and loading a dump are
  destructive and need a person to choose the moment (`backups.mdx` L77-95).

### 7. **`ship`** — put it live

**`check`** (the whole stage) → `step:mark` → `pnpm exec emdash migrate --status` →
`pnpm exec wrangler deploy` → `step:migrations` → `pnpm exec emdash whoami --url {{env.DEPLOY_URL}}`.
(`cloudflare.mdx` L85-93, `core-migrations.mdx` L16-28.)

- **`ship:undo`** — `pnpm exec wrangler rollback`, then `step:migrations`; it says that a rollback
  does not undo a migration (`core-migrations.mdx` L178).
- On Node the stage ends at the build and prints how to start it:
  `node --env-file=.env ./dist/server/entry.mjs` (`nodejs.mdx` L395-402).
- What must be true before a first deploy, and cannot be checked by a command today, is printed as
  a list — gap G6.

### 8. **`update`** — a newer EmDash

`step:mark` → `step:dump` → `pnpm outdated emdash @emdash-cms/cloudflare` →
`pnpm up --latest emdash @emdash-cms/cloudflare` → `step:build` → `pnpm dlx skills update`
(`updating.mdx` L333-365, `agent-skills.mdx` L322-329). It ends with the release-notes address and
the reminder that template files are not updated. Then **`start`** to see it run, **`ship`** to
deploy it.

### 9. **`emdash`** — anything else

`pnpm exec emdash` with whatever follows `--`. Content, media, menus, taxonomies, search, secrets.

## Not tasks, on purpose

- **Content** — people in the admin by their role; agents through `mise run emdash -- content …` or
  the site's MCP server with a scoped token (`ai-tools.mdx`).
- **Site code** — pages, queries, rendering, SEO, languages: written from the
  `building-emdash-site` skill; `check` verifies it.
- **People and access** — passkeys, login providers, invitations, Cloudflare Access: configuration
  and the admin (`authentication.mdx`).
- **Migrating from WordPress** — a one-off, with EmDash's importer and its two WordPress skills.
- **Themes** — a theme is a template; there is no theme command (`themes/overview.mdx` L8-10).

## Proven gaps — what official commands and mise cannot do today

| | gap | what the plan does |
|---|---|---|
| G1 | mise cannot skip a step that is already done, or branch on a flag | stages are split instead: `new` and `start`; `ship` and `ship:undo` |
| G2 | first-time setup, sample content and sign-in are one HTTP call or one click; there is no command for it | `start` shows EmDash's own Dev bypass link; an agent opens it |
| G3 | a Cloudflare template's local database is a file with a hashed name, so `emdash doctor` and `emdash export-seed` cannot be pointed at it; `export-seed` cannot read D1 at all | the model is recorded with `emdash types` instead; report upstream |
| G4 | no loop over `plugins/*` | plugin tasks take a name; Q3 |
| G5 | a registry plugin cannot be installed by a command and is not recorded in the repo | declare plugins in the repo with `plugin:add`; use the registry in the admin knowingly |
| G6 | deploy guards that need a file read: template names left in `wrangler.jsonc`, a stray `.dev.vars`, no site URL, the Worker Loader binding on a free plan | printed as a list by `ship`; propose them to `emdash doctor` upstream |
| G7 | one command's output cannot feed the next (the import plan digest, the migration fingerprint) | those are the two places EmDash wants a person to review; the stage prints the next command |
| G8 | ~~no background server, no stop~~ | **not a gap** — Astro has `dev --background`, `dev stop`, `dev status`, `dev logs`. Found on 2026-10-07 while testing; the nushell harness's daemon and the 2026-10-06 pid-file script both rebuilt it |
| G9 | the three OSes use different shells | every step is a plain `program arguments` line; proven per OS in stage 1 |
| G10 | adding a plugin ends with an edit to `astro.config.mjs` | the task prints the lines; the dev or agent makes the edit |
